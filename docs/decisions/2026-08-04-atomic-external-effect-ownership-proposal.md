# ADR: Atomic external-effect ownership

- Status: Accepted
- Date: 2026-08-04
- Decision owners: ATLANTIS AI program
- Applies to: provider-neutral external-effect execution and reconciliation

## Context

`executeExternalEffectWithReconciliation` currently provides durable receipt lookup, provider reconciliation, receipt validation, receipt persistence, and evidence emission. It does not atomically establish ownership before invoking `provider.execute`.

Two concurrent callers can therefore both observe a durable-store miss and a provider-reconciliation miss, then both invoke the provider for the same external-effect identity. Provider-side idempotency can reduce the consequence for some integrations, but the current provider-neutral contract does not require or prove it.

This decision remains provider-neutral. It does not select a production database, queue, cloud lock service, or provider SDK.

## Decision

ATLANTIS will use a bounded lease with an opaque ownership token and a monotonically increasing fencing generation for each normalized external-effect identity.

The operational-alpha non-owner policy is fail closed. A caller that does not own the current lease must never call `provider.execute`. It receives a typed ownership-conflict result that the governed workflow runner may checkpoint and retry only within its existing retry, deadline, cancellation, and budget controls.

Provider idempotency keys remain mandatory when the provider supports them, but provider idempotency is defense in depth rather than the ownership guarantee.

## Required invariants

1. At most one unexpired owner may execute a normalized external-effect identity at a time.
2. Ownership acquisition is atomic for one normalized identity.
3. Every successful acquisition returns an opaque claim token and immutable fencing generation.
4. A non-owner never calls `provider.execute`.
5. A committed receipt becomes the durable result returned to every later caller.
6. Expired ownership is recoverable through a new atomic acquisition with a strictly higher fencing generation.
7. A stale owner cannot renew, release, or commit after a newer generation has been acquired.
8. Claim, request, observation, and receipt identity validation remains fail closed.
9. Approval waits, cancellation, timeout, terminal budget exhaustion, and rejection do not retain indefinite ownership.
10. Provider commitment, receipt persistence, checkpoint persistence, and event append are not represented as one atomic transaction unless a later persistence decision actually provides that guarantee.
11. An uncertain provider outcome is not treated as a safe pre-execution failure.
12. Lease renewal cannot bypass the workflow deadline, cancellation state, or execution budget.

## Provider-neutral boundary

```ts
export interface ExternalEffectOwnershipStore {
  acquire(
    identity: ExternalEffectIdentity,
    request: ExternalEffectOwnershipRequest,
  ): ExternalEffectOwnershipResult | Promise<ExternalEffectOwnershipResult>;

  renew(
    claim: ExternalEffectClaim,
    request: ExternalEffectRenewalRequest,
  ): ExternalEffectClaim | Promise<ExternalEffectClaim>;

  commit(
    claim: ExternalEffectClaim,
    receipt: ExternalEffectReceipt,
  ): ExternalEffectReceipt | Promise<ExternalEffectReceipt>;

  release(
    claim: ExternalEffectClaim,
    reason: ExternalEffectReleaseReason,
  ): void | Promise<void>;

  observe(
    identity: ExternalEffectIdentity,
  ): ExternalEffectOwnershipObservation | Promise<ExternalEffectOwnershipObservation>;
}
```

The concrete types must carry normalized identity and the following minimum fields.

### Acquisition request

- `ownerId`: non-blank logical worker or execution-owner identity;
- `leaseDurationMs`: positive safe integer supplied by the composition root and constrained by its configured maximum;
- optional request correlation metadata that contains no secret material.

The store uses its authoritative clock. Callers do not supply `acquiredAt`, `expiresAt`, claim tokens, or fencing generations.

### Claim

- normalized external-effect identity;
- opaque claim token generated by the store;
- owner ID;
- acquired timestamp;
- expiry timestamp;
- immutable positive safe-integer fencing generation.

### Renewal request

- a positive bounded lease duration;
- no caller-supplied generation or replacement claim token.

A successful renewal preserves the claim token and fencing generation and only advances expiry. It succeeds only for the exact live claim before expiry. Renewal cannot resurrect an expired claim and cannot create a new generation.

### Release reasons

The initial contract must distinguish at least:

- `pre_execution_failure`;
- `cancelled`;
- `timed_out`;
- `budget_exceeded`;
- `approval_wait`;
- `rejected`.

`release` is idempotent for the exact claim and must not remove a newer generation. Release is allowed only when the caller knows the provider was not invoked or knows the provider did not commit.

If the provider was invoked and its commitment state is unknown, the caller must not immediately release ownership as though execution never occurred. The claim is retained until reconciliation establishes a receipt or authoritative lease expiry permits fenced recovery.

## Acquisition outcomes

`acquire` returns exactly one of:

- `acquired`: the caller owns a new or expiry-recovered lease and may continue toward provider reconciliation and, if still uncommitted, execution;
- `committed`: a validated durable receipt already exists and must be returned without provider execution;
- `owned`: another unexpired owner exists; the caller must not execute;
- `rejected`: the request or durable identity state is invalid or conflicting and execution must fail closed.

Every outcome includes the normalized identity. `owned` includes only the non-secret observation fields required for bounded retry policy; it must not expose an opaque claim token.

## Operation semantics

### Acquire

`acquire` atomically performs durable receipt observation, active-lease observation, expiry recovery, and new-claim publication for one normalized identity.

A recovery acquisition increments the fencing generation. Generations never decrease or repeat for an identity.

### Renew

`renew` verifies normalized identity, owner ID, opaque claim token, fencing generation, and unexpired ownership. It fails closed after cancellation, timeout, terminal budget exhaustion, approval wait, or any superseding generation as enforced by the caller and store boundary.

The composition root supplies maximum lease duration and renewal cadence. The workflow runner must stop requesting renewals when its own deadline or terminal controls are reached.

### Observe

`observe` is read-only and returns one of `unclaimed`, `owned`, or `committed`. It never grants execution authority and never extends a lease.

### Commit

`commit` atomically verifies the live claim token, fencing generation, normalized identity, and receipt identity; persists the committed receipt; and clears active ownership. It returns the normalized durable receipt.

A stale, expired, mismatched, or superseded claim cannot commit.

### Release

`release` removes only the exact live claim and records the supplied reason where the persistence implementation supports ownership history. It is safe and idempotent when the claim is already released, expired, committed, or superseded, but it never changes a newer claim.

### Provider reconciliation

After acquiring ownership, the owner reconciles with the provider before attempting a new effect. This is required for crash recovery and for recovery from a provider commitment followed by local persistence failure.

A reconciled provider receipt is identity-validated and committed through the same fenced `commit` operation. The owner executes only when durable observation and provider reconciliation both establish that no commitment is known.

## Ownership lifecycle evidence

The durable trace must distinguish, without overstating cross-store atomicity:

- ownership acquired;
- ownership contended;
- ownership renewed;
- ownership recovered after expiry;
- provider execution attempted;
- provider receipt reconciled;
- receipt committed;
- ownership released;
- stale-owner or invalid-state rejection.

Evidence append failure does not grant or revoke ownership. Ownership state remains authoritative in the ownership store.

## Operational-alpha policy

- Lease duration and maximum renewal duration are composition-root configuration, not hard-coded contract constants.
- Non-owners fail closed and may be retried only through governed checkpoint/retry behavior.
- A lease is not held across an unbounded approval wait.
- Cancellation, timeout, rejection, and terminal budget paths stop renewal and release only when provider state is known safe.
- An uncertain provider outcome waits for reconciliation or lease-expiry recovery rather than being treated as a clean release.
- Production persistence remains a separate architecture decision.

## Explicit non-goals

- Selecting Postgres, Redis, SQLite, a cloud lock service, or another production persistence technology.
- Claiming exactly-once behavior across the external provider and local stores.
- Holding a lease across an unbounded approval wait.
- Weakening authorization, budget, cancellation, deadline, or evidence controls.
- Expanding GitHub Actions or repository permissions.

## Acceptance tests required before integration

1. Two concurrent callers for one identity result in exactly one successful acquisition.
2. `provider.execute` is called at most once while one unexpired claim exists.
3. The non-owner does not execute and receives the typed fail-closed outcome.
4. A committed receipt is returned to all later callers without provider consultation.
5. An expired claim can be recovered by a new owner with a higher fencing generation.
6. A stale owner cannot renew, release, or commit after recovery by a newer owner.
7. A mismatched receipt, token, owner, identity, or generation fails closed.
8. Renewal preserves token and generation, is bounded, and cannot resurrect an expired claim.
9. `observe` never mutates ownership or grants execution authority.
10. A provider commit followed by local commit failure recovers through provider reconciliation without treating the uncertain outcome as a clean release.
11. Approval wait, cancellation, timeout, rejection, and terminal budget paths do not retain indefinite ownership or renew past terminal controls.
12. Ownership lifecycle evidence remains identity-bound, ordered, and honest about cross-store atomicity.
13. The governed composition-root test proves checkpoint, ownership, receipt, approval, and event boundaries cooperate across restart.

## Consequences

- The prior `load`/`save` receipt-store shape is insufficient for execution ownership and must not be extended with an in-process mutex presented as durable safety.
- Implementations require compare-and-set or transactional semantics capable of fencing stale generations.
- The workflow runner must handle typed contention without executing and within existing resource ceilings.
- Crash recovery depends on both authoritative lease expiry and provider reconciliation.
- Cross-store atomicity remains unresolved and must be represented explicitly in release evidence.

## Next implementation action

Implement the provider-neutral ownership types and store contract exactly as accepted here, followed by a deterministic in-memory reference store and focused concurrency, renewal, expiry, fencing, uncertain-provider-outcome, and lifecycle-evidence regressions. Integrate the verified boundary into protected resumable execution only after those contract tests pass.
